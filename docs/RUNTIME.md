# Runtime integration

`RuntimeSupervisor::cycle()` joins native-shaped configuration snapshots, the PHP challenge adapter, real network parsing/local-route checks, peer qualification, a log observation and the durable action coordinator. The native daemon connects these adapters in monitor mode. Both configuration saves and the daemon reject active recovery modes until real executors are implemented and validated.

Snapshot adapters must provide fresh settings, interfaces, VLANs, VIPs, native boot identity, uptime and explicit tri-state interlocks. Every required interlock must be known false. Maintenance, upgrades, any configured HA, another repair or shutdown stop collection and clear volatile confirmation. Configuration is compiled on every snapshot, and its effective hash plus boot identity defines the measurement context. Changing this context resets the peer baseline and policy episode while preserving durable budgets.

A second snapshot follows collection. Immediately before actions, the coordinator checks the same context again, including after evidence capture. Disable, mode, peer, interface or boot changes inhibit stale proposals. Wall-clock and monotonic-clock divergence greater than five seconds resets confirmation. The existing journal retains conservative action reservations.

The observation phase has a 25-second cooperative deadline checked between each bounded operation. It stops remaining collectors after an overrun and never calls the policy with a partially timed-out cycle. Native snapshot and log access use separate workers. This is not a hard wall-clock bound when the kernel cannot schedule or terminate a blocked process. Service-start adapters must not reuse the finite diagnostic descendant reaper.

The monitor daemon owns a separate exclusive supervisor lease, schedules nominal 15-second cycles without catch-up bursts and emits sanitized syslog messages only when status changes. TERM/INT inhibit actions and stop the loop. The rc script uses native `daemon` without automatic respawn, permits up to 35 seconds for graceful stop and reports failure if the process persists. It never force-kills an uncertain service PID. A saved configuration can therefore report an apply failure separately from successful persistence.

`LogWorker` keeps the file descriptor in a persistent child process. Requests carry a nonce, have a two-second deadline and accept only bounded tri-state replies. Errors terminate the worker; a replacement starts with a new log baseline. Its termination cannot overcome kernel-uninterruptible I/O. `ServiceState` creates the initial private journal only when the state directory is absent; an existing damaged or missing journal fails closed. Deinstallation preserves the state directory and budget.

## Bounded retry-log sampling

`LogRateProbe` reads new bytes from the regular native system log through a retained descriptor, at most 64 KiB per observation. The first observation skips existing contents. It counts only RFC3164-shaped `check_reload_status` records with the exact PHP-FPM socket failure message described in [Netgate issue 13252](https://redmine.pfsense.org/issues/13252). Embedded quotations from other programs and unrelated interface errors do not count. Alternate log formats are not yet supported.

A storm requires at least ten matching records per elapsed second, with an interval from five to 45 seconds. A bounded sample can prove this lower bound even when additional bytes were skipped. Otherwise, truncated coverage is unknown, never evidence of a quiet log. Context changes, long gaps, truncation, inaccessible files and symlinks invalidate measurements. Rotation reads the previously open file's new bytes, then opens the replacement at EOF; replacement history is not retroactively counted. There are no log-reader state writes or exported raw log lines.

## Native snapshot worker

`NativeSnapshot::read(new ProbeProcess())` invokes the CLI-only `native-snapshot.php` with a ten-second diagnostic deadline and 64 KiB output cap. It requires FreeBSD and native pfSense files. The helper uses `/etc/inc/xmlparse.inc` directly instead of the config boot/cache/backup loading path. Config input is limited to 8 MiB and checked for changes by file identity, size and hash around parsing. The helper does not write config.xml or refresh config.cache. It returns only whitelisted interface, VLAN, VIP and package fields; exception output is limited to fixed phase names.

Native boot identity comes from `kern.boottime`. Bounded `ps` output supplies conservative upgrade/package-manager, GUI-repair and shutdown process gates; PID 0 is a valid FreeBSD kernel record. The `/var/run/booting`, `pkg.dirty` and `pfSense-upgrade.pid` markers also inhibit. CARP VIPs and pfsync/XMLRPC HA configuration inhibit active recovery. Missing, malformed or truncated observations fail closed. These are fresh snapshots, not an atomic exclusion mechanism against every concurrent native operation; actual action adapters and supported-version lifecycle tests remain required.

Native sources inspected: [XML parser](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/etc/inc/xmlparse.inc), [HA configuration](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/usr/local/www/system_hasync.php), [upgrade PID/locking implementation](https://github.com/pfsense/FreeBSD-ports/blob/a621624266b19a7f48b1f94a60821d2c2fc6ee4c/sysutils/pfSense-upgrade/files/pfSense-upgrade).

The policy still requires a failed PHP transaction and corroborating local reachability/link conditions. A log storm alone never permits a reboot. A complete native runtime must validate log layout, interlock semantics, privilege boundaries, timing under load and durability across real package lifecycle operations.

## Durable diagnostic evidence

`DiagnosticJournal` uses a separate private StateStore under `/cf/conf/recovery_guard/diagnostics`, with atomic replacement and native file/directory synchronization. Package initialization provisions a new diagnostic directory or validates an existing journal; it does not erase damaged existing records. The latest 64 proposals are retained in insertion order. This is bounded incident evidence, not a notification delivery queue or a complete system log archive.

Each record contains only the proposal identity/kind, operating mode, time/uptime, native boot identity, configuration hash and tri-state observations. Additional input fields are discarded, and unexpected stored fields fail validation. Raw configuration, peer addresses, credentials and free-form logs are excluded. Duplicate records cannot change evidence or overwrite a final result. Rotation evicts the oldest record when the limit is reached.

The coordinator captures monitor proposals too and records `mode_inhibited` without executing an action. For active modes, capture still follows a fresh interlock check and precedes a second check and execution. A failed or ambiguous capture commit prevents execution. An ambiguous outcome commit prevents repair acknowledgement, so it cannot authorize subsequent reboot escalation. Uncertain executor completion is recorded as unknown when storage remains available. A pending record means no outcome was established; no record causes an automatic replay.

The configuration page displays these records and offers an authenticated, read-only JSON download through the same page privilege path. The export contains validated records only, sets no-store caching and returns an unavailable response rather than empty history on read failure. Actual pfSense rendering and authorization behavior remain native guest tests. Routine healthy observations do not create evidence records. Event notifications and reboot-result reconciliation remain separate work.

## Reboot handoff

`RebootDispatcher` is called while the coordinator owns the already-persisted budget reservation. `RebootHandoff::prepare()` requires a matching actionable diagnostic record, recovery mode and the exact reserved boot/time identity. It atomically stores a random one-use token in a separate private handoff journal. Dispatch returns `handoff_pending`, never `completed` or an executed-reboot claim. The coordinator records that unconfirmed status. No service-start or boot hook replays pending intents.

The native worker waits at most 35 seconds for the actual supervisor lease, using the same lock inode as ServiceLoop. It then owns the budget and intent locks, validates token/reservation/evidence, obtains a fresh native snapshot, and durably marks the intent consumed. Another fresh snapshot follows the commit. Enabled recovery mode, matching boot/configuration, clear maintenance/upgrade/HA/repair/shutdown gates and both wall-clock and monotonic age under 60 seconds are required. Missing/corrupt storage, a late worker, reversed clocks, stale configuration, competing workers and ambiguous claim commits inhibit execution. A consumed attempt is never retried, including after worker death.

`reboot-worker.php` uses native `system_reboot_sync()` only after these checks. Its native cleanup can stop packages because the original supervisor must already have retired. A returned routine does not establish a completed reboot. The current monitor daemon still refuses recovery mode and does not dispatch this worker; active-mode wiring, native cleanup collision tests, final outcome reconciliation and notifications remain release work. In particular, a process snapshot does not provide atomic exclusion against a native maintenance task starting immediately after the final check.

Twenty-five isolated FreeBSD handoff tests exercise the real locks and journals, synthetic fault measurements, fake reboot callbacks and competing forked workers. The separate real-reboot harness replaces only the reboot action with FreeBSD's shutdown command and uses actual boot identity. This proves the handoff can survive supervisor retirement and a real guest reboot; it does not prove pfSense package cleanup or release compatibility.

## Functional reconfirmation before reboot

The native reboot worker now uses RebootVerifier for both pre-claim and post-claim checks. Each verification first reads and validates the native configuration/lifecycle state, then performs a real local PHP transaction. A healthy or unknown PHP result stops collection. It probes the physical link and each exact configured peer through the existing direct-route/source-bound NetworkProbe. Any peer reply or uncertain result inhibits the destructive decision. It then rechecks the link, native configuration and PHP transaction.

The existing diagnostic record and unchanged configuration hash establish that these peers were qualified by the original monitor. The verifier cannot establish a new baseline or independently reserve an action. When the link is active, it starts a fresh log-reading interval and requires a newly observed storm after at least five seconds; historical records do not qualify. A confirmed down link supplies separate corroboration, so an unused log result is not required in that branch. An unknown link always inhibits.

Each verification has a 25-second cooperative deadline and wall/monotonic clock consistency checks; the handoff's overall 60-second wall and monotonic expiry still applies. Slow or numerous peers can exhaust the limit and inhibit reboot. This is an explicit safe failure, not a claim that all configured topologies always complete within the deadline. Native workers still need supported-version and real failure-condition validation. The final check reduces recovery races; it is not atomic exclusion against unrelated native maintenance starting afterwards.
